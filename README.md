# 出海雷达 · AI 出海营销助手

> 个人演示作品。面向出海营销服务商的**内部销售工作台**：从一批候选客户里挑出该跟的那一家，一路走到触达、方案、交付和复盘。

**定位说明**：这是给服务商内部的销售/运营用的工具，不是给客户看的营销 SaaS。所以界面是"工作台"（左侧客户列表 + 右侧步骤），不是官网。

**声明**：本项目为个人练习作品，与任何真实公司无关；文中出现的公司、人物、账号与投放数据均为虚构，仅用于演示。

---

## 一、它解决什么问题

出海营销服务商的销售链路有五步，每一步都靠人肉完成、且高度依赖个人经验：

| 环节 | 人肉做法 | 痛点 |
|---|---|---|
| 1 客户分析 | 翻官网、LinkedIn、融资新闻，凭感觉排序 | 慢、不可复现、新人不会做 |
| 2 客户联系 | 一人一版写私信/邮件 | 个性化成本高，最后都变成模板群发 |
| 3 方案撰写 | 套模板填空 | 千篇一律，销售讲不出差异 |
| 4 执行交付 | 方案到任务的翻译 | 销售承诺的，执行团队做不出来 |
| 5 数据复盘 | 看报表、凭经验拍结论 | 只说得清"效果不好"，说不清"卡在哪一层" |

这个 Demo 把这五步做成一条**可跑通、可解释、可复现**的链路。

## 二、快速开始

### 环境

- Python 3.10+
- 依赖：`streamlit`、`openai`、`pandas`

```bash
pip install -r requirements.txt
```

### 配置 API Key

Key **不写进代码**，有两种方式，任选其一：

**方式一：环境变量**（推荐用于长期开发）

```powershell
# 当前窗口临时生效
$env:DASHSCOPE_API_KEY = "sk-xxxx"
```

```cmd
:: 或永久生效（需重开终端）
setx DASHSCOPE_API_KEY "sk-xxxx"
```

**方式二：页面输入**（推荐用于演示，不落盘）

启动后，在左侧栏的输入框粘贴 Key 即可，Key 只存在于本次进程内存中，关闭即失效，不写入任何文件。

不配置 Key 也能跑——应用会进入**离线模式**，使用预置结果完整演示五步。

### 运行

```bash
streamlit run app.py
```

浏览器打开 http://localhost:8501 。

### 自测

```bash
python smoke_test.py
```

用 Streamlit 官方 `AppTest` 在无浏览器环境下跑通五步渲染与生成（16 项断言）。

## 四、五个步骤

### ① 客户分析：先跟谁，为什么

- **输入**：12 家客户档案（融资、招聘、TikTok 数据、投放状态、决策人）
- **输出**：四维打分排序 + 红黄牌 + 一句话判断 + 3 条理由 + 切入点
- **设计**：分数由规则算（可复现），理由由 LLM 写（可读）。**红黄牌是人工标注，与机器分分开存放**，最终排序 = 机器分 − 黄牌扣分，红牌出局。
- **看点**：表里会出现"目行 91.5 分排第二但被红牌否掉"——**分高不等于该跟**，这是这一步要展示的判断力。

### ② 客户联系：发什么，怎么跟

- **输出**：LinkedIn / 冷邮件 / WhatsApp 三版文案 + D0/D3/D7/D14 跟进节奏 + 回复意图分类
- **设计**：每版文案必须标注 **hook 来源**（引用了客户的哪条公开信息）。销售不敢发 AI 编的东西，但敢发"有出处"的东西。

### ③ 方案撰写：一页纸，销售讲 30 分钟

- **输出**：目标 / 现状判断 / 核心打法 / 内容矩阵 / 达人配比 / KPI（带行业基准）/ 三档报价 / 交付节奏
- **设计**：**结构化模板 + LLM 填肉**，而不是让模型自由发挥，否则写出来全是"赋能、闭环、抓手"。
- 支持导出 Markdown。

### ④ 执行交付：方案变任务，给一个样例

- **输出**：任务清单（负责人/截止/交付物/**可量化的验收标准**）+ 3 条 15 秒脚本分镜
- **设计**：验收标准必须可量化（如"3 秒完播率 ≥ 35%"），这是"交付"和"交差"的区别。

### ⑤ 数据复盘：判断效果，提出下一轮

- **输入**：模拟投放数据 + 方案里的 KPI
- **输出**：瓶颈定位（素材层/定向层/落地页层/offer 层）+ 因果链诊断 + 3 条动作 + **只改一个变量的 A/B 假设**
- **设计**：复盘不是"要优化"，是定位到某一层。

## 五、关键设计决策

1. **机器打分与人工红黄牌分离**
   分数可复现、可审计；红黄牌承载"机器看不见的判断"（已有代理、供应链崩了、刚被收购）。两者混在一起，就说不清一个结论到底是谁下的。

2. **规则负责打分，LLM 负责解释**
   让模型直接打分，同样的输入两次结果可能不一样，销售不敢用。规则算分 + 模型写理由，兼顾可复现与可读性。

3. **所有 LLM 输出强制 JSON**
   前端渲染代码与模型解耦；模型返回不合法 JSON 时能立即发现，而不是把一段散文塞进界面。

4. **离线兜底**
   没 Key、断网、额度用完，演示照样完整——这对"面试现场演示"是刚需，不是可选。

5. **不做向量库、不做 Agent 框架**
   1–2 小时的作业，单链路、12 条结构化数据，检索层没有收益。**范围控制本身就是工程判断**，写在这里是为了说明"为什么不做"。

6. **Key 只从环境变量读**
   仓库要公开，代码里不能有任何凭证。

## 六、数据说明

`customers.json` 中 12 家公司、人物、融资、TikTok 数据、投放数据**全部虚构**，仅用于演示，不含任何真实客户信息。

其中 12 家刻意做了分布：

- `c01 爪伴`：主案例，唯一走完五步；
- `c02/c06/c09/c12`：第二梯队，各有短板；
- `c03 目行`：分数很高但**已有成熟投放团队**，不该跟；
- `c07/c08`：教育订阅与开发者工具，**不该做 TikTok**；
- `c10 宠语`：数据漂亮但**供应链崩了**；
- `c11 家卫`：已被收购，预算冻结。

如果 12 家全是"完美客户"，第一步就没有判断力可展示。

## 七、局限与下一步

- 客户数据是手写的 mock，真实场景需要接官网抓取、融资数据库、广告库；
- 排序规则目前是固定权重，真实业务里应按行业/客单价调参；
- 没有持久化，刷新即重置（演示够用，多人协作不够）；
- 方案与复盘没有做 A/B 结果回流，闭环还是开环的；
- 未接入真实的达人报价库与投放 API。

## 八、AI 工具使用说明

这里说明 AI 参与的部分：

- **架构与代码**：由 AI 编程助手生成初稿，本人负责需求定义、业务设定、逐轮验证与取舍；
- **业务假设**：KPI 基准、报价区间等来自公开资料与行业常识推断，**未经真实客户校准**，实际执行需运营复核；
- **文案与 prompt**：AI 生成，人工筛选与修改；
- **测试**：冒烟用例由 AI 编写并执行；
- **数据**：全部为虚构，未使用任何真实客户信息。
